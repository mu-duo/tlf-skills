## 背景

用户与 agent 讨论测试治理后，要求先把已对齐的倾向记录为 issue，推迟其中的哲学讨论，并把「把测试方案打包为一个可选 skill」作为候选方向。本条目为 `suggestion`（无状态、无 history），归宿是 ADR / PDR / 删除；本文只忠实沉淀已对齐内容，不构成实现授权，也不改动 workflow 或创建 skill。

## 已达成倾向（跨项目默认，项目可覆盖）

> 本节记录用户已对齐的政策倾向；打包与落地方式见「待讨论问题」。

### 边界与成本
- 规则为跨项目默认，项目可在自身文档中覆盖。
- 保留关键风险验证，不因降本而放弃。
- 把「执行成本 / 维护成本 / 上下文成本」分开管理，不混为一个总量指标。

### 测试与 PDR 的映射
- 任何持久化测试用例都需要有 PDR 引用（允许一个 PDR 对应多个用例，多对一）。
- 发现无映射的旧测试时，登记（register）它，而不是删除；不静默丢弃既有验证。

### 开发与测试更新相互独立
- 开发与测试更新是相互独立的两件事，不默认绑定。
- 普通任务不得新增 / 修改 / 删除持久化测试，也不得改动 fixtures / snapshots / helpers / runner 配置 / 验收脚本 / skip 列表，或任何会改变验证语义的阈值。
- 普通任务可以运行项目已授权的既有检查，以及合规的、非持久化的临时探针；但不得绕过闸门（gate）。
- 普通任务按 PDR / 风险维护一份去重、精简的候选清单，每条包含：PDR 或 pending、行为、原因 / 来源；并显式报告本次增量。

### 测试更新的触发与授权
- 测试更新必须由用户显式触发，并且要确认范围；范围未指定时先询问。
- agent 自主选择「最小充分且有用」的验证，而不是所有候选；不以覆盖率 / 数量指标为要求；优先高影响项与历史缺陷。
- 报告时区分新增 / 修改 / 删除 / 未采纳，并给出 PDR 理由。
- 已批准的行为变更，仅在授权的更新范围内可据以修改测试；遇到模糊或相互冲突的契约要询问，不得为了「变绿」而弱化测试。

### 验证入口与报告
- 项目声明其验证入口 / 执行策略；支持外部的用户工具；绝不自动创建与之竞争的工具链。
- 默认读结构化摘要（含执行版本 / 范围、计数、跳过 / 缺口、失败指针）；必要时才看有界、分组的失败详情，再定向读源码 / 日志；不批量读取通过的用例。
- 缺失 / 过期 / 部分的报告不算「全部通过」。
- 区分「已实现」与「已验证」；可以带着显式的阻塞性验证缺口结束任务，但绝不称「已通过」。
- 候选被整合 / 拒绝后从活动清单中移除，不计为已验证。

### 生效前提（OPT-IN，最新限定）
- 该治理**仅在**用户在面向 agent 的项目文档（如 `AGENTS.md`）中显式声明存在 / 启用测试工作流时，才 OPT-IN 生效。
- 不得从存在测试目录、或加载了某个 skill 来推断其已启用。
- 无声明时：不自动创建该治理、不收集候选、不维护候选清单、不提醒更新。
- 既有验证要求、用户的直接命令、以及失败如实披露，仍然适用。
- 有声明时，agent 可以显式告知用户「测试应更新」，但该提醒**不授权**更新。
- 项目声明候选路径 / 验证入口；必要时就缺失的配置向用户询问。
