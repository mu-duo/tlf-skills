# 仓库原型

端到端链路并不总是 `main` -> handler -> service。写 `01-map.md` 之前先识别原型；错误的原型会产生一条看起来合理、却教错心智模型的链路。本文件决定把哪些入口和哪条链路放进那份 brief；链路本身属于那里，不属于对话。

## 快速识别

| 树中的信号 | 原型 |
| --- | --- |
| `Dockerfile` + `routes/` / `handlers/` + 服务启动引导 | HTTP 服务 |
| `cmd/<name>/main.go`、`argparse`、`click`、`cobra`、`bin/` | CLI |
| `src/index.ts` 导出函数，没有 `main`，发布 `package.json` / `pyproject.toml` | 库 / SDK |
| `consumers/`、`subscribers/`、`handlers/` 以事件名组织，broker 配置 | 事件驱动 / 队列 |
| 注册表、`plugins/`、`providers/`、DI 容器装配、`@Inject` | 插件 / DI 容器 |
| 多个 `packages/` 或 `apps/`，各自有清单 | Monorepo |
| `dags/`、`jobs/`、`stages/`、`transform/`、schema 文件 | 数据管道 |
| `.proto`、`.graphql`、schema 优先的目录、`generated/`、`*_pb2.py` | 重度代码生成 |

## HTTP 服务

**入口：**服务启动引导（`main.go`、`app.py`、`server.ts`）、路由注册、中间件链、健康检查。

**一条链路：**请求进入 -> 路由匹配 -> 中间件 -> handler -> service/use-case -> repository/DB -> 响应形态。

**什么会让自顶向下阅读失效：**

- 中间件全局注册，且离路由很远。即使 handler 从不提及，链路也包含它。
- 装饰器或框架魔法（`@app.route`、自动装配）隐藏了分发跳。
- 一个仓库里有多个服务（公开 API、管理后台、worker），各自独立启动。
- 前面有网关或代理重写路径。

先追中间件列表，再看 handler。大多数「这个字段为什么不见了」的 bug 就住在那里。

## CLI

**入口：**`main` 加上命令树。真正的入口是用户运行的子命令，不是二进制。

**一条链路：**argv 解析 -> 命令分发 -> 选项校验 -> 核心调用 -> 输出/退出码。

**什么会让自顶向下阅读失效：**

- 框架的命令树由许多文件组装。读 `main` 看到的是注册，不是行为。
- 全局 flag 或配置文件在命令执行前合并。
- 共享的 `RunE` / `run()` 辅助函数隐藏了真正的工作。

选最接近 `focus` 的子命令。从参数解析开始的链路往往很无聊；说出来，并从命令主体开始。

## 库 / SDK

**入口：**公开表面——`index` 导出、`__init__.py`、`lib.rs` 再导出、`package.json` 中的 `exports`。

**一条链路：**公开调用 -> 编排层 -> 内部核心 -> 副作用或返回值。

**什么会让自顶向下阅读失效：**

- 公开 API 只是薄包装；真正的复杂度在往下三层。
- 带版本的目录（`v1/`、`v2/`），其中只有一个在用。
- 功能开关选择不同的实现。
- README 记录的 API 比代码导出的旧。

从用户会调用的导出符号开始，而不是从目录树开始。

## 事件驱动 / 队列

**入口：**生产者位置（publish/emit）、消费者注册、broker 的 topic 或队列名、schema 定义。

**一条链路：**触发 -> 发布 -> broker 跳 -> 消费者 -> handler -> 副作用。这是一条中间有缺口的链路；broker 不是代码。

**什么会让自顶向下阅读失效：**

- 没有单一调用栈。用「查找引用」追踪会停在 publish 调用处。
- topic 名是字符串，常常动态构建或来自配置。同时 grep 字面量和配置键。
- 重试、死信队列和幂等包装改变了实际顺序。
- 一个 topic 多个消费者；用户只关心其中一个。

绝不要在这里猜链路。问是哪个事件、哪个消费者，并说明除非能看到配置，否则 broker 跳是 `inferred`。

## 插件 / DI 容器

**入口：**容器启动引导和注册清单。行为在运行时装配。

**一条链路：**启动引导 -> 注册 -> 解析/注入 -> 插件钩子 -> 效果。

**什么会让自顶向下阅读失效：**

- 调用 `new Foo()` 什么也找不到；实例由容器构造。
- 接口实现由配置、profile 或环境选择。
- 钩子按名字或注册表查找调用，而不是直接调用。
- 装饰器或宏生成装配代码。

先追注册，再追解析出的实现。如果绑定依赖配置，记录两种可能的实现，并把当前生效的标为 `inferred`。

## Monorepo

**入口：**工作区清单（`pnpm-workspace.yaml`、`turbo.json`、`go.work`、`Cargo.toml` workspace），然后是一个包的入口。

**一条链路：**一个包的边界 -> 内部调用 -> 依赖包 -> 效果。链路跨越包边界，这正是重点。

**什么会让自顶向下阅读失效：**

- 多个 app 名字重叠；顶层 README 只描述其中一个。
- 共享包被所有东西使用（`common/`、`shared/`、`core/`），于是「查找引用」返回噪音。
- 构建工具重写 import 或给路径起别名。
- 两个包里有重复实现，其中一个已废弃。

把地图限定在链路上的包。覆盖一切的 monorepo 地图是目录，不是心智模型。

## 数据管道

**入口：**DAG 定义、调度器注册、作业入口脚本、stage 列表。

**一条链路：**源读取 -> 变换 stage 1..n -> 校验 -> 写出到 sink。

**什么会让自顶向下阅读失效：**

- 管道是被声明的，不是被调用的；顺序来自 DAG 或 stage 列表。
- schema 才是真正的契约，而它们位于代码之外。
- 回填与重处理路径不同于正常运行。
- 幂等和分区逻辑改变了「一条记录」的含义。

让一条记录穿过各个 stage。记录每个边界上的 schema；漂移就发生在那里。

## 重度代码生成

**入口：**schema（`.proto`、`.graphql`、IDL）或生成器配置。生成的文件是输出，不是源。

**一条链路：**schema 定义 -> 生成器 -> 生成的类型 -> 手写的消费方。

**什么会让自顶向下阅读失效：**

- 生成的代码被提交进仓库，看起来像手写的；读它学不到持久的东西。
- 生成器添加了 schema 中从未出现的行为（校验、序列化）。
- 重新生成发生在构建步骤中，所以提交的输出可能已过时。
- 字段编号、线格式或保留名承载着代码中看不见的含义。

锚定 schema，而不是生成输出。在地图中明确标出生成路径，以免有人去改它们。
