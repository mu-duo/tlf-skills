# 内置：tdd

> 该能力的唯一来源，按本文执行，不调用外部 skill。
> **优先级**：`docs/agents/testing.md`（skill 内 `references/testing.md`）高于本文。本文只管循环怎么转；期望从哪来、断言要多强、什么时候改测试，以测试准则为准。

用途：用最小步长把行为写出来，并锁住它。

## 循环

1. **定 seam（公共边界）**：先确定测试从哪个公共边界进入——不伸手进内部拿状态，也不绕过接口去查库。边界没定就先和用户定，别急着写。
2. **写红**：加一个会失败的用例。它读起来像需求：说清「应该发生什么」，不说「内部怎么实现」；一个用例只锁一个行为。
3. **写绿**：写刚好够通过的实现。不顺手加「以后可能要用」的功能。
4. **切下一片**：一个用例 → 一小段实现 → 再一个用例。不要先把测试铺满再一次性实现。

重构不属于这个循环。行为锁住之后，重构交给评审阶段（有 `code-review` 就按它走）。

## 期望值从哪来

期望值必须能独立于实现成立：手算的例子、规格里的数字、已知正确的字面量。

不要用被测代码的算法反推期望——那样的断言只是把实现抄了一遍，永远不会反驳它。

## 哪些依赖可以替换

只在系统边缘替换：外部服务、时间、随机、文件系统、数据库（优先用真实库，确实不可控时才替）。自己写的类、模块、内部协作者一律不替。

边界要好替：外部依赖通过参数传进来；接口按操作拆分，不要一个万能 fetcher 挂一堆开关。

## 三种常见坏味道

- **绑实现**：行为没变，改个内部结构测试就红。
- **断言恒真**：期望值由构造过程保证，测试永远是绿的。
- **横向铺测试**：一次写一批想象中的用例，测的是形状，不是用户能看到的行为。

边界形状本身拿不准（模块该多深、切口在哪、接口暴露什么）时，先把这些问题和用户谈清，再写第一个用例。
