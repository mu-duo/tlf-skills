# Domain Modeling（领域建模）

> 轻量精简版，裁剪自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 domain-modeling（MIT License, Copyright (c) 2026 Matt Pocock）。若环境已安装同名完整 skill，请优先使用完整版。

在设计的同时**主动**构建并打磨项目的领域模型。这是主动的纪律：质疑术语、构造边界场景、在术语和决策成型的那一刻就把它们写下来。（只是为查词而读 `CONTEXT.md` 不算本 skill——那是任何 skill 都能做的一行习惯；本 skill 用于**修改**模型，而不只是消费它。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文，由它指向每个上下文的位置。

**惰性创建**：只在有内容可写时才建文件。没有 `CONTEXT.md`，就在第一个术语确定时创建；没有 `docs/adr/`，就在需要第一条 ADR 时创建。

## 会话中的动作

- **对照词汇表质疑**：用户用词与 `CONTEXT.md` 冲突时立刻指出。「你的词汇表把 cancellation 定义为 X，但你说的似乎是 Y，到底是哪个？」
- **锐化模糊表达**：用户用含糊或一词多义的词时，提出精确的规范术语。「你说的 account 是指 Customer 还是 User？这是两回事。」
- **讨论具体场景**：讨论领域关系时用具体场景压力测试，逼用户把概念边界说清楚。
- **与代码交叉验证**：用户描述某处如何工作时，核对代码是否一致；矛盾要当面提出。「你的代码取消整个 Order，但你刚说可以部分取消，哪个对？」
- **立即更新 CONTEXT.md**：术语一确定就当场写入，不要攒批。

`CONTEXT.md` 必须完全不含实现细节：它是词汇表，不是 spec、草稿本或实现决策仓库。

## CONTEXT.md 格式

```md
# {上下文名称}

{一两句话说明这是什么上下文、为什么存在。}

## Language

**Order**：
{一或两句话的术语描述}
_Avoid_: Purchase, transaction
```

规则：

- **有主见**：同一概念有多个词时，选最好的一个，其余列入 `_Avoid_`。
- **定义紧致**：最多一两句，定义它**是什么**，不是**做什么**。
- **只收本项目特有概念**：通用编程概念（超时、错误类型、工具模式）不进，哪怕项目大量使用它们。
- **自然成簇时可分子标题**；单一内聚领域用平铺列表即可。

## ADR

ADRs 放在 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`。编号时扫描现有文件取最大号加一。

**模板极简**（一条 ADR 可以只有一段）：

```md
# {决策的简短标题}

{1-3 句：背景是什么、决定了什么、为什么。}
```

价值在于记录**做过这个决策**及其**原因**，而非填满小节。可选小节仅在确有价值时加：`Status` frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）、Considered Options、Consequences。

**仅当以下三条同时成立才提议写 ADR**：

1. **难以逆转**：以后改主意的代价可观。
2. **无背景会令人意外**：未来的读者会想「当初为什么这么做？」
3. **是真实取舍的结果**：确有替代方案，且有特定理由选中这一个。

缺任何一条就跳过——容易反悔的将来直接反悔即可；不意外的没人会问；没有替代方案的记下来也只是「我们做了显而易见的事」。

典型合格情形：架构形态；上下文间的集成模式；带锁定的技术选型（数据库、消息总线、认证、部署目标）；边界与范围决策（显式的「不做」同样有价值）；刻意偏离常规路径的做法；代码里看不见的约束；拒绝理由非显然的替代方案。
