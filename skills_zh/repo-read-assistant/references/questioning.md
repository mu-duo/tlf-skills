# 提问

对话验证的是用户已经读过的模型。它不交付模型。下文每个提示都假设已经先交付了一份 brief。

## 把话说得平实

用户没有读过这个 skill。它的词汇是给你用的，不是给他们用的。

| 内部说法 | 改说 |
| --- | --- |
| brief、层 | 「我给你写的那一页」/「这一遍」 |
| 模型检查 | 「几个问题」 |
| 预测 | 「在你查看之前：你预期会怎样？」 |
| 细化 vs 披露 | 什么都不说——绝不提方法的名字 |
| 预算 | 什么都不说——简要即可 |
| spine、chain | 「一个请求经过的路径」 |
| L0-L4 | 什么都不说——绝不口头评级 |
| 锚点 | 「打开 `path:line`」 |

规则：

- 一个问题只含一项。四路匹配题是考试，不是检查。
- 问用户刚刚读过、说过或问过的东西。
- 每次都给出退路：「或者说你不知道。」
- 如果用户直接提问，先回答。绝不要把答案扣在检查后面。
- 初次接触时，用一句话说一次：「读这个，然后我问几个问题——答错的地方就是缺口。」之后不再提方法的名字。

## 阅读时带着的一个问题

交付 brief 之前，只给一个问题。它不在对话里被回答；用户阅读时带着它，读完后反馈。在零模型的情况下，预测只会得到「我不知道」——所以不要要求用户预测他们尚未读过的内容。

好问题指向层，而不是某个细节：

- 「阅读时一直问自己：回路中的哪一步你会先改，它会扰动什么？」
- 「带着这个问题：请求在哪里改变形态，哪个模块负责那次改变？」
- 「阅读时想：为什么这被拆成两个服务而不是一个？」
- 「带着一个问题：如果队列停止消费，最先坏的是什么？」

规则：

- 恰好一个问题，一句话。
- 它必须能从 brief 中回答，而不是靠既有知识。
- 不要用回答来换取文件。把路径和问题一起交付。
- 如果用户立刻回答了，简短确认并让他们继续读；真正的检查在后面。

## 读后的模型检查

三个问题，按此顺序。它们检验模型，而不是对名字的记忆。

**1. 定位。**「对于 <feature>，你会从哪里入手，之后是哪两个文件？」路径错了，说明地图层没有落地，无论他们把想法解释得多好。

**2. 预测影响。**「如果我们在这里改动 <X>，还有什么会动，谁先察觉？」这检验关系：事实对、关系错的模型会在这里失败，上限为 L2。

**3. 解释为何——以及为何不。**「为什么这样构建，而不是 <显然的替代方案>，这个选择付出什么代价？」后半句才是真正的问题。没有代价的设计选择是口号。

措辞：

- 「不看那页：一个典型任务要经过哪些步骤？」
- 「哪个实体连接 <A> 和 <B>，它在两者之间携带什么？」
- 「要添加 <Y> 你需要动什么，什么可能悄悄坏掉？」
- 「设计者在这里决定不支持什么，这换来了什么？」

规则：

- 三个问题在同一条消息里提问，编号。它们是一次检查，不是三轮。
- 接受错误答案，不要粉饰。记录下来，然后纠正。
- 如果三个都答对，记录证据然后继续；不要凭空加第四个。
- 如果前两个失败，停下。模型还不到位；先纠正 brief 再问更多。

## 回讲与白板提示

最强的信号，也是评级成本最低的。

- 「用两句话把它讲回给我，就当从没见过这个仓库。」
- 「凭记忆画出模型：一句话、回路、名词、接缝。」
- 「你会用 30 秒对新同事说什么？」
- 「在空白页上重画回路，然后标出你最不确定的地方。」

按顺序、关系和省略项来评级。流畅的含糊不是掌握；记为低准确度、高置信度。框对箭头错的图至多是 L2。

## 过载处理

brief 过载和对话过载是两个不同的问题。

| 信号 | 可能原因 | 应对 |
| --- | --- | --- |
| 读完后说「内容太多了」 | brief 对其层来说太密 | 拆分，或把细节下移一层；不要缩短文字 |
| 读到一半停下 | 实质上超了上限 | 把 brief 裁到它的层，并说明什么下移了 |
| 对话里回复很短或只「嗯」 | 对话轮次太长 | 缩到一个问题，<=150 字 |
| 不回答或转移话题 | 检查高于模型当前水平 | 降到定位类问题 |
| 反复跳过 | 用户今天到此为止 | 停下，写状态，下次坐下再继续 |

绝不要靠把 brief 压缩成文字来应对过载。密度是层的问题：把细节移到 `02-structure.md` 或 `03-operations.md`，或拆分该层。

## 处理「直接告诉我」

当轮就照办。不讨价还价。

1. 直接回答，引用 brief 中的锚点。
2. 停止当前 brief 的检查。
3. 本次会话中不要再次问同一个问题。
4. 会话结束时问一次：「下次要问题吗？」在用户主动提起之前，「不要」是最终答复。

把降级记录在会话记录和 profile 中，以免下次会话重开争论。

## 处理「我不知道」

对双方都成立。

- 用户：给出最小的可判定问题（「同一个文件还是另一个文件？」），或指出 brief 中回答它的那一节。同一个点两次未中后，直接修正 brief。
- Agent：「我还不确定；`path:line` 处的代码暗示 X，但我还没确认调用方。」然后去验证或标记为 `inferred`。绝不要用看似合理的架构填补空白。

## 问题质量检查

发送问题之前：

- 它能用一两句话回答吗？
- 它是否有一个能提供信息的错误答案？（是/否问题通常没有。）
- 它是否指向某一节 brief 或某个文件，让用户知道去哪里看？
- 它是本轮的唯一个问题吗？
- 它是否遵守上限：每次 brief 检查三个问题，每个对话轮次一个？
