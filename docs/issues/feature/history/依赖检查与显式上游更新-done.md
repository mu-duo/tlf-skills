## 方案（简述）

- 依赖**先检查 / 列出**，再询问。
- 默认（无 flag）：交互式（stdin + stdout 均 TTY、非 dry-run）仅对**缺失**的受支持名称询问一次；同意只授权**安装缺失项**，**不**更新已有。No / 回车 / 非 TTY → 缺失项回退轻量版。全部存在 → 不询问；部分存在 / 缺失 → 先报告再只问缺失。`--force` 单独不更新外部依赖。
- 显式 `--with-matt-skills`：**更新**受支持的 8 个外部上游依赖 + 补缺失；不询问，提示本地修改可能被覆盖；命名集合之外的外部目录保留；第一方自带集合不提交上游，但仍照常执行普通第一方全目录同步（不被绕过）。
- **安全**：上游 `skills` 无 `--dir`，仅**默认 codex 全局目标**（含 realpath 等价）可安全调用；**仅非等价 `--dir` / 未验证 agent** 在写入前拒绝并给出手动更新指引；普通自定义 `--dir` 安装仍保留已有依赖、为缺失项装轻量版，不给出误导性上游询问。
- **失败（非原子）**：`add -y` 覆盖、无 `--force add`；以窄名称集合 + `--json` 逐个检测；已有依赖更新**可能部分成功且包装器不恢复**；缺失项上游失败可回退轻量版，**已有依赖更新失败不回退轻量版**，显式更新失败非零、不报成功；已知安全目标上确认成功者记为 upstream-owned，失败保留原归属。
- 第一方复制回滚保留；上游需 Node >= 22.20；不新增安装的 Python / 工具。
