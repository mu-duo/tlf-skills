# 内置：domain-modeling

> 该能力的唯一来源，按本文执行，不调用外部 skill。

用途：把模糊说法收敛成稳定的项目词汇，并在决策定型时留下记录。

只有**改动**模型时才走本文。为了查词而读 `CONTEXT.md` 不算。

## 触发时机

- 同一个概念有多种叫法，或一个词指多个概念。
- 讨论里出现「大概就是那个东西」这类指代。
- 准备写 issue / SPEC / 测试名，却发现找不到准确的词。
- 出现了一个值得长期记住的取舍。

## 动作

1. **找到词表**：根目录有 `CONTEXT-MAP.md` → 按它定位相关上下文的 `CONTEXT.md`；只有根 `CONTEXT.md` → 单上下文；都没有 → 等第一个术语定案时再创建，不提前造空文件。
2. **当场对齐**：
   - 用词与词表冲突 → 停下问「以哪个为准」；
   - 词义含糊或一词多义 → 给出更精确的候选名；
   - 讨论概念关系 → 用具体场景压边界（谁在什么情况下用它、与相邻概念差在哪）。
3. **立刻写入**：术语一锤定音就更新词表，不攒批。
4. **需要留决策**：满足判据才写 ADR（见下）。

## 词表写法

```md
# {上下文名}

{一两句：这是什么上下文、为什么单独成篇。}

## Language

**Order**：
{一两句：这个词指什么。}
_Avoid_: Purchase、transaction
```

规则：

- 一个概念只留一个正名，同义词归入 `_Avoid_`。
- 定义回答「是什么」，不回答「怎么做」；一两句封顶。
- 只收本项目特有的概念；通用编程词汇（超时、异常、工具函数）不收。
- 不写实现细节——这是词汇表，不是规格书。

## ADR 判据

三条同时成立才写：

1. 改回来的代价高；
2. 不了解背景的人会觉得意外；
3. 是真实取舍，不是唯一解。

缺一条就不写。位置 `docs/adr/`，文件名 `NNNN-slug.md`，四位编号，取当前最大值 +1，编号不复用。

```md
# {一句话标题}

{一到三句：背景 → 决定了什么 → 为什么。}
```

可选小节按需：`Status`、`Considered Options`、`Consequences`。本仓库的 ADR 生命周期以 `references/adr.md` 为准，冲突时以它为准。
