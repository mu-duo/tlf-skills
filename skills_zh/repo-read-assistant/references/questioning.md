# 提问

措辞就是机制。一个用户躲不掉的预测，抵得上十段解释。

## 预测提示

在揭示之前提问。绝不要把问题和一个包含答案的提示放在一起。

- "在我展示之前：你觉得哪个模块处理 X，为什么？"
- "在这个仓库里，一个请求到达 X 时，它碰到的第一个文件是什么？猜一下。"
- "如果你今天要加 Y，你会先打开哪个目录？选一个。"
- "你预期在 `path:line` 会看到什么？一句话。"
- "这两个里面哪个是入口点，你为什么选它？"
- "数据在哪里改变形状：在边界上还是在核心里？"
- "如果我们删掉这个函数，什么会坏？"

规则：

- 每轮恰好一个预测。
- 接受错误答案，不要软化它；把它记为证据，然后揭示。
- 如果用户拒绝猜，就问最小的可能问题（"同一个文件还是另一个文件？"），而不是在没有预测的情况下继续。

## 苏格拉底式追问，三个层级

当用户给出正确但浅薄的答案时使用。在他们犹豫的那一层停下；那就是他们理解的边界。

1. **What** — "这个函数返回什么，谁来消费它？"
2. **Why** — "为什么它在这里，而不是在调用方？"
3. **What if** — "如果它返回 null 会坏什么？谁先发现？"

在某个概念上能过第 3 层的用户是 L3 或更好。卡在第 2 层的用户是 L1-L2，需要的是锚点，而不是更多正文。

## 反向讲解提示

最强的信号，也是评分成本最低的。

- "用两句话跟我复述一遍，就当我是从没看过这个文件的人。"
- "凭记忆画出这条链：只写名字，不许看。"
- "关于这个文件，你会用 30 秒跟新同事说什么？"
- "如果这在生产环境坏了，你先去哪里看？"

按顺序、锚点和遗漏来评分。流利的含糊不是掌握；记为低 `accuracy`、高 `confidence`。

## 降档措辞

过载是无声的。留意它，在它固化之前回应。

| 信号 | 回应 |
| --- | --- |
| 回答变短 | "我们缩小到一个文件。打开 `path:line`，只告诉我第一行做什么。" |
| "mm"、"sure"、"ok" | "这听起来像没核对就说了 yes。一个问题：这个函数接收什么？" |
| 答非所问或转移话题 | "先放下那条线。回到一件事：哪个文件处理 X？" |
| 反复跳过 | "跳过是一个信号，不是失败。我们停掉新材料，复习两个你已经见过的术语。" |
| "This is a lot" | "同意。这次会话还剩一个概念，然后我们写入状态就停。" |

然后显式削减预算：一个概念变成零个新概念，一个代码块变成一个锚点，一段话变成一句话。不要宣布要改变教学法；直接缩小。

## 处理 "just tell me"

在同一轮内照办。不协商，不说 "but you'll learn more if"。

1. 用 L1 直接回答，并给出锚点。
2. 针对当前目标停止预测循环。
3. 本次会话稍后不要重复问同一个问题。
4. 会话结束时问一次："下次恢复预测吗？"答案是否，就在用户主动提起前一直算最终决定。

把降级记录到会话文件和 profile 中（该目标的 `mode`），这样下一次会话不会重新挑起争论。

## 处理 "I don't know"

对双方都有效。

- 用户：给出最小的可判定问题，或在两次答错后直接讲这个点。绝不把同一个问题问得更响。
- Agent："我还不知道；`path:line` 的代码暗示是 X，但我还没确认调用方。"然后去验证或标记 `inferred`。绝不用貌似合理的架构来填补空白。

## 问题质量检查

发送问题之前：

- 它能用一两句话回答吗？
- 它有没有一个能提供信息的错误答案？（是/否问题通常没有。）
- 它是否指向一个文件或上一个回合，让用户知道去哪里看？
- 它是这一轮里唯一的问题吗？
