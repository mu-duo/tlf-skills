# PDR 产品规格

PDR = 目标态产品规格（「产品规格书」）：产品当前生效的最终目标——其模块、对外契约与机制设计。只记录已确认的约束（粗或细）；已实现的细节不会自动提升进 PDR。默认方案；可在项目副本中覆盖。

## 结构

- 模块目录按阅读顺序编号（例如 `01-architecture/`、`02-ui/`）。根 `00-README.md` = 概览 + 模块索引 + 阅读顺序。
- 每个模块：
  - `00-README.md`——角色 / 范围边界 / 依赖 / 文档地图。
  - `01-spec.md`——功能需求，每条带 `FR-<MODULE>-NN` ID 与验收判据。FR ID 稳定且永不复用；每个模块内编号连续。
  - `02-interfaces.md`——接口契约。提供方模块拥有其对外接口；消费方引用它们。
  - `03-nfr.md`——非功能需求。
  - `design/`——可选的机制级设计，**不参与编号**。
- 跨模块架构与调研材料可放在模块外目录。
- PDR 树不包含现状或进展材料：没有 `04-current.md`，没有当前进展章节。现状是**平级树**（`current.md`）。

## 目标与差距→issue

- **PDR 就是目标。** `NN/01-spec.md` 持有目标态；每条记录的需求——无论粗或细——都是已确认约束，而不是未知/未确认的分类。没有单独的目标文件；最终形态细节位于模块规格中。
- **根 README 是概览/导航。** 它承载最终形态概览、模块索引与阅读顺序，并链接平级的 Current 树；不包含进展章节。
- **变更按类型分流。** 目标变更仅在经过对齐后才更新 PDR；带理由与权衡的决策归入 ADR（见 `adr.md`）。已对齐范围内的实现自主推进，遵守 ADR、契约与安全；高成本、破坏性或难以回退的决策先与用户确认。已实现的细节不会自动回流到 PDR。
- **差距 → issue。** 在规划步骤，agent 读取 PDR 目标与 Current 现状（`current.md`），推导**候选**任务（模块 / FR、建议类型、切片、验收判据），由用户挑选。差异只是候选——可能是漂移、质量差距、未验证行为或目标过时，不一定是缺失功能。已满足的粗粒度目标仍可细化；不要臆造差距。被采纳的候选落到 `docs/issues/`，其关联记录模块 / FR。不因空闲而自动创建 issue。
- **非目标是范围边界。** PDR 可以将非目标 / out-of-scope 项表述为正向的范围边界；在 ADR 否定决策策略下，它们不是被拒备选方案，也不需要逐条理由。

## PDR ↔ ADR 边界

- PDR = 产品应该是什么（目标态）。
- ADR = 带理由与权衡的决策。PDR 可以用**描述性短语 + 稳定路径链接**指向 ADR（例如 `支持[离线使用](../../adr/0003-offline.md)`）；描述独立撰写，**不**转述或概括 ADR 的理由。不要求每条需求都挂 ADR，本方案绝不自动推断 ADR 链接（见 `rendering.md`）。
- suggestion 的采纳会归入 ADR 或 PDR（见 `issues.md`）。

## PDR ↔ Current 边界

- 两棵独立、用户可读的文档树：`docs/pdr/`（目标）与 `docs/current/`（实际建成形态）。互不内嵌。
- 模块可以按名称对齐，但不做文件/段落镜像；显式地以多对多方式链接模块 / FR 引用。两树之间的**语义 / 导航 / 契约链接**是预期之中的——使用普通相对 Markdown 链接。见 `current.md`。
- PDR 与 Current 都处于默认渲染范围内，与完整 ADR 集一起；见 `rendering.md`。

## 示例（DA_AGENT）——不属于通用规则

DA_AGENT 是此模式的一个具体实例：模块 ui / agent / cpp-core / FPGA，另有 architect 与 research 作为模块外区域；每个模块使用规格层 `00-README / 01-spec / 02-interfaces / 03-nfr` 加不参与编号的 `design/` 子区；FR 前缀为 `FR-AGENT-NN`、`FR-UI-NN` 等；产品场景位于单独的 `07-scenarios.md`。来源：DA_AGENT ADR-0026。
