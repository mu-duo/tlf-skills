## 用户的原始模型（保留，作为本条出发点）

- 项目的状态空间巨大。
- 模糊的 PDR 把可行状态约束到一个粗略区域（coarse region）。
- 用户此前的表述：该区域内的任一状态都满足 PDR。
- 随着 PDR / ADR / 功能的持续演化，约束不断收窄，直到逼近理想需求。

> 以上是用户原始模型，本轮保留，作为本条出发点；后续决定与它并列，不替换原始表述。

## 本轮已确认的决定（2026-10-14）

> 与上方原始模型并列，不替换原始表述。

- 每个已写下的 PDR 即为有效目标：写下的 PDR 就是要被满足的目标，而非待补全的草案。
- 用户拒绝在 PDR 内部引入「未知 / 未确认」类别：不把状态分成已确认 / 未知 / 未确认，也不要求某状态先被标记为「确认」才承认它满足 PDR。
- 区分在于粒度 / 解空间大小，而不是「确认 / 未确认」：粗略 PDR 对应更大解空间，精细 PDR 对应更小解空间。
- 「Web UI exists」是合法的粗略需求：粗略 PDR 足以开工；实现反过来给用户刺激，促使其细化出更细的 PDR。
- 不必在实现前补齐全部细节。
- Agent 在授权任务内自主，尊重既定约束；对重大 / 昂贵 / 破坏性 / 难以回退的选择，先向用户询问。
- 当前实现细节永不自动上升为 PDR：实现选择不会因已实现就变成需求。
- 用户原始模型保留，见上。

### 文档形态的决定（已确认，供实现参考）

> 与 [拆分Current与精简任务日志](../../feature/history/拆分Current与精简任务日志-done.md) 的实现相关。

- PDR 与 Current 是彼此独立、用户可读的并列文档树。
- Current 携带基线（baseline）+ 版本 / 置信度。
- 模块以链接方式指向 PDR / Current，而不镜像其内容。
- 任务历史记在 issues / git；Current 不写日志（ADR 等文档自身的 Log 不受此限）。
- Current 在 baseline 推进时同步，并在任务收尾回顾时检查。
- Current 不再受「≤1 页」上限约束。
- 不做 ADR / PDR 初始化。

## 仍未确认的质疑（2026-10-14 复核）

> 上一轮 agent 提出、至今仍未被用户确认的内容，单独保留。用户未接受此前全部质疑。

- 「字面上不违反」不等同于「实际被接受」——在本模型中的位置仍待澄清。
- 分类残余：agent 曾建议区分「偏好未知 / 授权自由 / 已确认约束」；其中 PDR 内的「未知 / 未确认」类别已被用户拒绝（见上），但该分类与「粒度 / 解空间」观点如何对应尚未谈定。
- 非单调演化：探索可以扩展或修订约束，而不只是单调收缩——单调性尚未谈定。
- 测试保护的边界：测试应保护「已确认的承诺」还是每一个实现选择——属测试治理范畴，本条不作裁定（见 [测试治理与可选Skill](测试治理与可选Skill.md)）。

> 上一轮质疑中的「实现选择不应自动成为需求」本轮已确认（见「当前实现细节永不自动上升为 PDR」），故移出未确认列表。
