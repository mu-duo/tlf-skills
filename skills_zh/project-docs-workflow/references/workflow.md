# 开发流程

默认方案。项目可在物化的 `docs/agents/workflow.md` 中覆盖；该副本决定运行时行为。

开发单个 issue 的默认形态：对齐、构建薄切片、填充细节、加固、然后同步文档。该流程是推荐——项目可覆盖任一步骤——但在使用时，其唯一硬性规则是对齐与规划先于实现。

## 工作单元与粒度

- 工作单元是 **issue**（见 `issues.md`）：一个 feature 级交付物。bug / chore 使用相同形态，简化处理。
- **粒度是建议**，绝不强制：把切片定到可单次 review 的推进单元（≈0.5 人天启发式），按任务弹性调整。
- **阶段切分由 agent 自行感知**——下一步做功能的哪个切片，绝不落成目录或文件；唯一的物化跟踪是 issue 自己的 `## 步骤` 清单。issue 内可选的一行备注可以明确当前阶段。

## 读什么

- **人读**：产品 L1（`docs/prd/00-README.md`），再模块 L1（`docs/prd/<NN-模块>/00-README.md`）——仅用于建立理解，不含实现细节。
- **agent 事实源**：L2 规格文件（`01-spec` / `02-interfaces` / `03-nfr` / `design/`）加 Current 的实际建成事实。
- **导航**：`docs/prd/00-index.md` 与各模块 `00-index.md`，用于模块地图、阅读顺序、约定与追溯。
- **L1 不是事实源。** L1 与 L2 冲突时，以 L2 为准。

## 对齐

- **先对齐后构建**：只有对齐完成且计划 / 步骤写好后，才开始实现（对齐 → 计划与步骤 → 构建）。
- 对齐是**对话式、软性的**：不冻结，不设仪式性的「已对齐」记录。需求变化时（功能需求漂移）主动重对齐。
- 方向有歧义时，调用 `grilling`（未安装则按 `references/deps/grilling.md` 执行）；`grill-me` 仅入口别名；`grill-with-docs` = `grilling` + `domain-modeling`（兜底 `references/deps/grilling.md` + `references/deps/domain-modeling.md`）。
- **差距分析**在此处（规划阶段）进行：读取 L2 目标与 Current 现状，推导**候选**任务（模块 / FR、建议类型、切片、验收判据），由用户挑选。差异只是候选——可能是漂移、质量差距、未验证行为或目标过时，不一定是缺失功能；不要臆造差距。不因空闲而自动创建 issue。
- **范围内自主**：一旦对齐，agent 在约定范围内自主实现，遵守 ADR、契约与安全；高成本、破坏性或难以回退的决策先与用户确认。

## L1 阅读顺序与维护

- **人类**：产品 L1 → 模块 L1。L1 是 L2 的人类叙事视图；读者不需要读 L2 就能建立整体理解。
- **agent**：用 `00-index.md` 导航 → L2 规格文件 + Current 获取事实。
- **L1 绝不覆盖 L2。** L1 是派生、有损的，不新增约束。冲突 → 以 L2 为准。
- **混合维护**：变更影响叙事时增量打补丁；基线前移、模块增删、累计 ≥10 次补丁或人类要求时整体重生成。始终展示 diff。
- 保留不可见标记 `<!-- narrative-source: <L2 revision>; generated: <date> -->`。
- 人类评审 L1 diff 的可读性与事实合理性；无需阅读 L2。

## 叙事影响触发

收尾时（以及规划目标变更时）检查这四项。不设逐 FR 元数据，也不新增跟踪产物。

1. L1 引用到的 FR 发生语义变化 → review / 更新 L1。
2. 新增或变更的 FR 改变用户可见行为 → 新增 / 更新 L1。
3. 纯内部改动 → L1 不动，记一行 Log。
4. 目标用户 / 核心场景 / 范围 / 非目标变化 → 更新 L1。

## 变更协议

- **目标变更**：规划 → 先改 L2 → 在同一可 review 单元内更新 L1 → 人类在生产实现前 review L1 diff 与目标范围（软检查点；沉默不等于同意）→ 实现 → 收尾 Current。
- **范围内实现**：L2 / L1 不动 → 直接实现 → 收尾 Current。
- **内部改动 / bug 修复**：L2 / L1 不动；行为变化则更新 Current；若 bug 暴露出目标错误，升级为目标变更。
- 原型 / spike 在方向确认前豁免。
- 已实现的细节不会自动提升进 L2 或 L1。

## 范围收敛

- **默认偏好：收敛功能空间。**「功能空间」是用户面向的别名，指由 PRD 约束的状态空间 / 解空间；不要引入第二个概念。
- **触发条件 = 改变功能 / 范围目标的决策**，位于 PRD / ADR 层（定义目标之处）或 issue 规划层。
- 未被现有 PRD 覆盖的 feature 候选属于**扩张**：提出前先用一句话说明理由。实现现有 PRD 的候选属于收敛 / 实现，不需要额外理由。
- 恢复或维持既有行为的 bug 修复与 chore 豁免。若 bug / chore 实际改变了功能集合，应重新归类为 feature。
- 这是偏好，不是门禁：不新增产物、不阻断。项目可以覆盖。
- **记录策略**：默认不记录被拒备选方案——见 `adr.md`（否定决策）与 `issues.md`（`-drop` 归档）。本策略只约束持久记录；对齐 / grilling 仍可探索备选方案。

## 五步流程

1. **规划 / Plan**——细化验收判据，设置步骤清单状态，写 1–2 句方案。产出最小；不新开章节。差距分析在此进行，读取 L2 目标与 Current；L1 仅作人类理解参考。
2. **骨架 / Skeleton**——最小可运行的垂直切片（忽略输出 / 格式打磨）；留下一条运行证据并展示给用户——首个 review 点。纯修复可跳过（在 Log 注明理由）；feature 与结构性工作必做。
3. **细节 / Details**——主路径实现、细节补全、代码质量。`tdd`（未安装则按 `references/deps/tdd.md` 执行）是可选的内部循环。
4. **异常 / Exceptions**——主路径之后的失败路径、边界与稳定性。真实开发中的阻塞立即处理并记 Log，绝不排到本步骤。
5. **回顾 / Wrap-up review**（收尾回顾）——issue 完成时的轻量文档同步清单（prd L1/L2、current、adr、context、issues、agents）；若无需更新，记一行 Log。仅做文档同步；会话 / agent 复盘属于 `retro`（未安装则按 `references/deps/boundaries.md` 执行）。

## 进度与续接

- issue 条目带有 `## 步骤` 清单（五步）；**就地**更新。Log 只记录关键事件（范围变化、阻塞、交接、放弃），不记录每次步骤变化。
- **会话是软性的。** 会话是用户的注意力窗口；节奏由用户掌握（他们可以在 issue 之间新建 / 压缩会话）。agent 不得吞并超出对齐范围的工作。
- **恢复时**，先读 issue 的步骤与 Log，再与用户确认续接点。

## 文档同步钩子

- **规划**：差距 → issue 候选落到 `docs/issues`；条目的关联记录模块 / FR。
- **收尾回顾**：
  - **L1 检查**（四项叙事影响触发）：引用到的 FR 语义变化、用户可见行为变化、或目标 / 范围移动 → 打补丁或重生成 L1 并展示 diff；否则记一行说明 L1 无变化。另做机械检查：L1 中引用的每个 FR ID 都存在于 L2（缺失 → L1 漂移：修正 L1；仅当属于目标变更时才加入 L2），且 L1 不含外部链接或状态标记。
  - **Current 检查**：确认已完成的变更包含在选定基线内。是 → **就地**更新受影响的 Current 文档——只改事实，绝不插入指向 issue 的自链接或任务历史；否 → 保持不动，并在 issue 中记录待同步项。基线前移会刷新相关 Current 文档；实际状态未变 → 不修改。
  - **prd（L1 / L2）**：L2 目标变更与 L1 更新落在同一可 review 单元。
  - 变更需要时，触及 `adr` / `context` / `issues` / `agents`。
- **归档**：完成 / 放弃时按 `issues.md` 归档 issue。

## 边界

- 大规模或高风险多阶段工作 → `deepwork`（未安装则按 `references/deps/boundaries.md` 执行）；绝不与本流程叠加。
- `tdd`（未安装则按 `references/deps/tdd.md` 执行）嵌套在细节内；seam 确认并入规划对齐（不设第二道门禁）。
- `retro`（未安装则按 `references/deps/boundaries.md` 执行）负责会话 / agent 复盘；第五步仅做文档同步。
- 文档 HTML 渲染可选且手动（`rendering.md`）；它绝不作为本流程的一部分运行——文档编辑时不自动构建。关于本方案如何与这些 skill 并存，见 `coexistence.md`。
