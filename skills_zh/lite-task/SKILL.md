# 轻量任务

面向**小型、低风险任务**的轻量开发工作流。它保留 `project-docs-workflow` 的步骤纪律，但去掉其文档义务：不强制创建 issue 条目，不做 PDR / Current / ADR 记录。通常只产出代码。

## 何时使用

- 小型、低风险且**不**改变跨模块契约的任务；或
- 用户明确选择启用此轻量工作流。

否则使用 `project-docs-workflow`（或项目自身物化的工作流）。如果轻量任务实际上需要持久的文档状态——一项决策、一次契约变更、一条状态记录——停下来升级到 `project-docs-workflow`；不要在这里悄悄写文档。大型或高风险的多阶段工作不在此范围；请使用 `project-docs-workflow`（或 `deepwork`）。

## 五个步骤

与 `project-docs-workflow` 步骤集合和意图相同，产出更轻：

1. **功能同步 / Sync** — 与用户对齐功能范围和验收标准（相当于 `project-docs-workflow` 的规划）。优先收敛：新的功能 / 范围候选需要一句话说明理由；bug / chore 工作豁免。只有完成对齐后才开始实现。
2. **骨架 / Skeleton** — 最小可运行的垂直切片；留下一条运行证据并展示给用户（首个 review 点）。纯修复可跳过。
3. **实现 / Implement** — 主路径实现、细节补全、代码质量。
4. **异常 / Exceptions** — 主路径之后的失败路径、边界与稳定性。真实阻塞立即处理。
5. **回顾 / Wrap-up** — 简要自检。仅在变更确实需要时同步文档（见下文）。

步骤由 agent 感知：不要求物化为文件、目录或 issue 清单。

## 文档边界

- **不要求创建 issue 条目**，也没有强制的 `## 步骤` 跟踪。
- **不要求更新 PDR / Current / ADR。**
- 通常唯一的产物是代码和 git 提交信息。
- 如果出现持久决策或契约变更，升级到 `project-docs-workflow`，而不是就地写文档。

## 与 `project-docs-workflow` 的关系

- 每个任务只选**一种**流程；绝不叠加两种。
- 步骤名称和意图相同；区别在于文档义务（本流程：默认无）。
- 当任务变大（契约变更、跨模块影响、持久决策）或用户要求带文档的流程时，升级到 `project-docs-workflow`。
